# 使用 Claude 对 DSH 动态路由进行双向验证

## 目的

在开发和校准阶段，当规则边界、任务标签、模型质量或失败归因存在不确定性时，可以在 DSH 中调用 Claude 作为独立评审者。Claude 不替代生产路由器，也不作为每次请求的必经步骤；它用于发现遗漏假设、构造反例和形成争议样本。

## 2026-08-27 首次实验

实验在真实 DSH 页面中明确选择 `Claude Sonnet 4.6`，要求其独立审查六项优化，并输出优先级、赞成或反对理由、最小验证、风险和必须由产品负责人完成的事项。

Claude 给出的优先级为：

1. P0：图片真实产物验收与设置弹窗排查。
2. P1：累积低置信度、规则与分类器分歧、用户负反馈样本。
3. P1：拆开任务分类正确率与最终模型质量。
4. P2：有条件地增加分模型额度探针与长冷却。
5. P2：有条件地引入时间衰减与样本量置信区间。
6. P3：谨慎让分类器修正实际路由分数。

该排序与当前实现方向基本一致。Claude 额外指出：用户反馈存在选择偏差；任务标签不能由路由器自身循环定义；分模型额度可能实际共享同一池；时间衰减不能替代突发故障检测；分类器放量必须具备明确回滚条件。

## 实验暴露的两个关键问题

### 1. 评审会话必须隔离

最新 DSH `141eb6f` 的“新会话”入口在本次浏览器验收中只关闭侧栏，没有切换到空白会话。评审请求因此继承了旧会话中的图片和视频任务。Claude 虽然收到“不调用工具”的要求，仍先处理旧任务并调用了图片与视频工具。

后续双向验证必须满足以下任一隔离条件：

- 创建全新 DSH 会话并验证消息数为零；
- 使用独立 API 会话 ID；
- 对评审输入构造无历史消息的请求；
- 若无法证明隔离，则评审结果标记为 `context-contaminated`，不可直接成为训练标签。

### 2. 能力画像必须区分原生能力与工具辅助能力

本次实验中，`Claude Sonnet 4.6` 作为文本模型通过 `image_generate` 工具成功产生图片文件。这不能证明 Antigravity 原生图片模型验收通过，但证明“任务可完成能力”不等于“模型原生能力”。

建议将能力画像拆成：

- `nativeCapabilities`：模型接口直接支持的文本、视觉理解、图片生成、视频生成等能力。
- `toolAssistedCapabilities`：在特定 Agent preset 和工具集合下可间接完成的能力。
- `requiredTools`：完成该能力依赖的工具名称和认证状态。
- `executionPath`：`native-model`、`agent-tool` 或 `hybrid`。
- `pathAvailability`：模型额度、工具额度、订阅登录和运行权限的联合可用性。

路由解释也应明确展示执行路径，避免把“Claude 调用了图片工具”解释成“Claude 原生支持图片生成”。

## 推荐工作流

1. 先由规则、轻量分类器和真实执行形成主判断。
2. 只将低置信度、规则与分类器分歧、用户负反馈或设计争议样本送给 Claude。
3. 使用隔离会话，隐藏主判断和预期答案，要求 Claude提出反例与遗漏假设。
4. 保存 `ruleDecision`、`classifierPrediction`、`claudeReview`、`executionOutcome` 和 `userAdjudication`。
5. Claude 与主判断一致时只增加证据，不自动视为真值。
6. 发生分歧时进入争议集，由真实执行、固定 rubric 或人工标注裁决。
7. 只有裁决结果进入离线校准；Claude 原始意见保留为证据，不直接作为训练标签。

## 建议的数据字段

```json
{
  "reviewMode": "claude-independent",
  "reviewContext": "isolated | context-contaminated",
  "reviewModel": "claude-sonnet-4.6",
  "ruleDecision": {},
  "classifierPrediction": {},
  "claudeReview": {
    "taskLabel": "",
    "confidence": 0,
    "risks": [],
    "disagreesWithRule": false
  },
  "executionPath": "native-model | agent-tool | hybrid",
  "executionOutcome": {},
  "userAdjudication": null
}
```

## 何时不调用 Claude

- 已被硬能力约束明确判定的请求。
- 高置信度且已有充足真实样本的低风险任务。
- 只需要读取精确额度或确定性运行状态的问题。
- Claude 与待评估模型共享同一数据来源、无法形成独立证据时。
- 无法隔离会话上下文时。

## 产品负责人需要确认的事项

1. 图片产物的合格标准，例如任务完成、主体符合、文字可读和视觉质量的最低门槛。
2. 模型输出质量 rubric，建议至少拆为正确性、完整性、指令遵循、成本和延迟。
3. 用户反馈语义，区分“回答质量差”“路由选择不合适”“额度信息错误”和“工具执行失败”。
4. 额度探针预算，包括每日次数上限、最小间隔和允许消耗的订阅额度。
5. 分类器放量与回滚门槛，包括最低样本量、置信度阈值、允许影响的任务范围和回滚指标。

## 建议的首轮门槛

以下数值用于启动讨论，不是未经确认的生产承诺：

- 累积至少 100 条真实 shadow 请求。
- 人工独立标注其中至少 20 条争议或低置信样本。
- 分类器只在置信度不低于 0.85、margin 不低于 0.25 时进入候选放量集。
- 初次放量只允许小幅分数修正，不允许绕过硬能力和精确模型冷却。
- 每个隐藏额度模型每日主动探针不超过 2 次，运行失败产生的被动反馈优先于主动探针。
- 任一任务类别的质量负反馈率相对基线显著上升时立即退回 shadow。

## 当前结论

Claude 双向验证值得保留，但必须是低频、隔离、可追溯的开发评审机制。首次实验本身已证明：若缺少会话隔离和执行路径建模，评审模型可能被旧任务污染，同时将工具能力误归因给模型能力。
